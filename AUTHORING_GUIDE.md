# Authoring Guide

How to write a chapter of *LLM Serving from Scratch* without breaking the two things that make
the book credible: measured numbers, and code that matches the prose.

## Quick start

```bash
npm install -g "mystmd@$(node -p "require('./package.json').devDependencies.mystmd")"
pip install -r requirements.txt -r requirements-dev.txt
pre-commit install

myst start          # live preview at localhost:3000
./scripts/ci-check.sh   # exactly what CI runs
```

The book builds with **Jupyter Book 2**, whose engine is the `mystmd` CLI — that is what `myst`
is. It comes from npm and is pinned in `package.json`; there is no second copy in
`requirements.txt` on purpose.

## The chapter template

Every chapter follows the same nine-part shape (PLAN.md §12.1). The stubs are already generated
with these headings and per-chapter guidance in `[To write: …]` brackets. Do not reorder them —
the repetition is what makes 29 chapters read as one book.

1. **Header block** — tier, prerequisites, the scorecard row this chapter moves
2. **The problem** — a measurement from the previous chapter that is unacceptable
3. **The idea** — the mechanism from first principles, with arithmetic
4. **The build** — incremental implementation
5. **The measurement** — harness re-run, new row, why it moved
6. **The cost** — what this made worse. **Mandatory**
7. **Key takeaways** — 3–5 bullets
8. **Looking ahead** — sets up the next chapter's problem
9. **Further reading** — `@citekey` against `references.bib`

## Two rules that are not negotiable

### Never paste code into prose

Quote it from the working tree so it cannot drift:

````markdown
```{literalinclude} ../llmserve/cache/blocks.py
:language: python
:start-at: "class BlockAllocator"
:end-before: "class BlockTable"
```
````

Anchor on `:start-at:` / `:end-before:` text, never on line numbers — line numbers rot on the
first edit above them.

### Never type a number into prose

Numbers come from `bench/results/*.json`, generated by `python -m bench.run_v01` and stamped with
model, hardware, versions and date. Declare the table you want in `bench/scorecards.py`, render it,
and include the fragment:

```bash
python3 scripts/render-scorecards.py          # write chapters/_generated/*.md
python3 scripts/render-scorecards.py --check  # fail if a committed fragment is stale
```

````markdown
```{include} _generated/ch05-kv-cache.md
```
````

**Chapters contain no executable cells.** An earlier draft rendered these tables by executing
Python during the book build. That works, but it makes every deploy depend on a Jupyter kernel, a
torch install, and a server that refuses to start as root — failures that have nothing to do with
the book. Generating fragments ahead of time keeps the invariant that matters (no number typed into
prose) while making the build pure markdown, and lets CI *diff* the regenerated output, which
catches staleness that execution would happily paper over.

Two scripts enforce it, both run by `ci-check.sh`:

- `scripts/verify-numbers.py` — every cited result exists and carries its stamps, and none predates
  the engine code it measures.
- `scripts/render-scorecards.py --check` — every committed fragment matches what the results say.

## Cross-references

Chapters carry a label matching their number, so refer to them as
`[ch08](#ch08)`. Appendices use `[Appendix B](#appendix-b)`. MyST resolves these at build time
and the build fails on a broken reference — which is the point.

## Definition of done

A chapter keeps `[DRAFT]` in its title until all of the following hold (PLAN.md §12.3):

- [ ] Code merged into `llmserve/`, passing `ruff` and `pytest` on CPU
- [ ] Equivalence test added for any behaviour-affecting change
- [ ] Scorecard row regenerated from a committed result file
- [ ] Checkpoint tag pushed, `CHECKPOINTS.md` updated
- [ ] "The cost" section written
- [ ] Cross-references and citations resolve; `myst build --html` clean
- [ ] `[DRAFT]` removed

## Style

British English, second person, active voice, short sentences. Mathematics only where it predicts
something the reader then verifies. Diagrams must show a mechanism, never decorate. Every number
carries its conditions: hardware, model, dtype, request rate, trace, date.
